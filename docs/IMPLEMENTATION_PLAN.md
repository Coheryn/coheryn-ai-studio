# Coheryn AI Studio — Implementation Plan

This document tracks implementation gates and remaining release requirements without deadlines or duration estimates. The current macOS ARM64 CPU implementation includes native text generation, packed quantized kernels, independent single/batch embeddings, CLI/API transport, adaptive admission and S0–S6 managed text-session/tool/schema/sampling/batching capabilities. The exact Qwen2-VL FP16 pair now supports native image-to-text, managed component identity, secure bounded ingress, image-aware planning, private original assets, opt-in image-history persistence and cooperative CPU scheduling. The current workspace passes 255 ordinary tests; eight model opt-ins and a child-process test entrypoint remain separate. Detailed historical checkpoints and their evidence follow below.

The initial A0/A1 slice now routes standalone text through a native adapter registry and shared model interface. The prioritized Qwen3.5-0.8B CPU text adapter introduces bounded single/indexed Safetensors reading, BF16 weight tiles and hybrid recurrent/full-attention execution. See [ADAPTERS.md](ADAPTERS.md) and [QWEN35.md](QWEN35.md) for exact scope. This is development evidence, not completion of the format/architecture gates. Existing GGUF fixtures and release obligations remain unchanged.

The immediate priority is [CPU production hardening](CPU_RELEASE.md) for the existing implementations: source-bound native checks, abrupt-process recovery, instrumented fuzzing, dependency review, verified offline packages and actual three-platform model/resource qualification. Production labeling remains blocked until that evidence passes review. Managed Qwen3.5 checkpoint/text/image/session/planner work is recorded in the later A2/B1–B4 checkpoints below. Broader independent reference/EOS/long-context coverage remains open. Additional architecture and GPU expansion follows this scoped CPU qualification work. The remaining A0–A5/F0–F5 matrix, retained LLaVA and selected Gemma CPU graphs, Metal and complete release qualification retain their requirements. Image understanding, independent embeddings, native GGUF plus both Safetensors layouts, CLI/API, adaptive memory and CPU/GPU acceleration remain mandatory.

## Review decisions

- Keep independent Rust execution, native GGUF, memory-aware admission, mandatory CLI/API and optional GUI. Add native image input → text output as P0 through separate preprocessing, vision encoding and multimodal integration modules alongside text inference.
- Start memory limits, cancellation and bounded buffers in G1, before the server exists.
- Pin external reference tools and numerical tolerances before accepting optimized execution.
- Inspect actual tensor types, graph dimensions, tokenizer semantics and template bytes; family names and filenames are insufficient compatibility evidence.
- Use the publisher FP16 reference file first. Use F32 numerical fixtures and a reproducibly derived F32 development artifact. Required quantized execution follows in G4.
- Preserve all C01–C23 release requirements and C24 image understanding; retain C25–C28 embedding inference/API/CLI/RAG interoperability and add C29–C38 session/tool/constraint/batching and independence/presentation requirements. A CPU-only or text-only preview does not constitute full v1.0.
- Retain mandatory Metal qualification for the pinned 0.5B model in FP16 and Q4_K_M and the selected LLaVA/Qwen-VL variants under M0–M2/G5. The exact Qwen2-VL CPU checkpoint is qualified only within its published scope; LLaVA, Metal and full VLM/platform acceptance remain open.
- Separate structural support from exact evidence; removing a qualification whitelist never removes byte integrity or authorizes unknown semantics, advanced features, model-supplied code or an external execution fallback.
- Make both Safetensors layouts mandatory alongside GGUF, with no merge/conversion requirement. Format parsers feed shared native architecture descriptors and tensor storage; source configuration/tokenizer/processor mappings and every numeric encoding still need explicit support and qualification. Sharding alone neither compresses weights nor provides distributed inference.

## Validation and release rules

- Fast checks: parser/shape fixtures, tokenization/templates, numeric kernels, sampling, admission, cancellation, stop handling and cleanup.
- Model checks: pinned-file logits, layers and greedy outputs separately for every qualified encoding/backend. Never label mere parsing as inference compatibility.
- Safetensors checks (planned): single/indexed header and asset validation, independent BF16 operations, complete lossless tensor/layout parity, source-weight text/vision/embedding numerics, contained shard ownership, atomic management, interrupted writes and resource cleanup. Qualify source-format/precision changes separately from executor correctness; no silent packed-layout interpretation or precision conversion.
- Embedding checks (planned): exact dimensions, tokenizer/masks/pooling/normalization, individual/batch and CPU/Metal vector parity, explicit truncation, quantized executor/quality separation, CLI/API/SDK/RAG interoperability, peak memory and bounded batch/error/cancellation behavior.
- Image checks: pinned processor pixels/tensors/patches, vision features, projected embeddings/positions and image-conditioned logits/greedy text; single/multiple images, reordered parts, resolutions, formats, component mismatches, Base64/URL security, admission and stage cancellation. Reference tools stay outside production dependencies.
- Security/lifecycle: fuzz hostile metadata; request/auth/path/download limits in G2; repeat requests/cancellations/swaps and active unload tests before release.
- Memory/performance: contexts 128/512/4096 where admitted; concurrency one/two; balanced/low-memory profiles after implementation; cold/warm only when controlled. No speed or memory advantage claim without comparable evidence.
- Default development is CPU-first on macOS ARM64, one inference session, no telemetry. Reject infeasible requests rather than changing context or semantics.
- Maintain the C01–C38 evidence checklist, including A0–A5 and F0–F5 acceptance, session/cache/store/tool/schema/batching, clean-environment independence and controlled-name CI gates. GUI, audio, image generation, video, architectures beyond the mandatory text/VLM/embedding and selected Gemma CPU targets, additional unqualified formats/packed schemes, CEAP, speculation and SSD paging remain outside mandatory core delivery.

See `RELEASE_CHECKLIST.md` for current evidence and outstanding gates. A checked-in workflow or fuzz target does not prove that its external campaign ran.
