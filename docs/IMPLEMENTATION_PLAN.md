# Coheryn AI Studio — Implementation Plan

This document tracks Coheryn AI Studio’s implementation gates and remaining release requirements. Delivery follows dependency and acceptance gates, without deadlines or duration estimates. G0/G1 and the initial G2 text-only CPU service are implemented. G3 now has CPU hardware probes, deterministic profiles, atomic queue-to-session reservations and observed engine buffer capacities. M0 provenance/contracts are implemented as groundwork, with independent vision capture and full asset qualification still open. G4 now implements native packed kernels and controlled row parallelism; E0 reference inputs are prepared. E1 implements native Nomic CPU embeddings; E2 adds standalone/client CLI, embeddings API, shared scheduling, atomic file export and tested external RAG/vector-store interfaces. S0 now supplies automated source/path, locked-graph, archive-integrity and current-host executable checks. S1 implements ephemeral owned text histories, revision/idempotency controls, exact context selection, CLI/API lifecycle and streaming cleanup. S2 now adds isolated bounded KV reuse; S3 adds opt-in versioned embedded histories, restart/replay, lazy pages and atomic import/export. S4 now implements an exact-file native tool profile, lossless arguments, SDK/SSE/CLI support and tool-aware histories. Next is S5 constrained output and expanded sampling, with remaining M0/M1 image work before M2/G5. Broader platform/package/license qualification remains open. Image understanding and independent single/batch embedding inference, `/v1/embeddings`, embedding CLI and external RAG interoperability are mandatory for full v1.0. Image execution remains unimplemented; embedding CLI/API CPU evidence is separate from text and does not qualify Metal or other platforms.

Stateless operation remains supported; optional full RAG, semantic memory, GUI and agent orchestration remain separate.

Historical reference workflows and numerical results below retain their original scope; independently managed assessments must be separated from the native source/build/test/runtime chain under the new policy. The engineering plan records initial naming/provenance conflicts, including immutable tokenizer assets. Resolve conflicts without changing tokenization, standardized identifiers or required notices. Original source assets and historical captures have now been relocated intact; active external builders/captures are removed from the native chain. Source/path and current-host binary checks pass, with CI enforcement configured. This is scoped automated evidence, not completed G6 license/security/package or broader-platform qualification.

## Review decisions

- Keep independent Rust execution, native GGUF, memory-aware admission, mandatory CLI/API and optional GUI. Add native image input → text output as P0 through separate preprocessing, vision encoding and multimodal integration modules alongside text inference.
- Start memory limits, cancellation and bounded buffers in G1, before the server exists.
- Pin external reference tools and numerical tolerances before accepting optimized execution.
- Inspect actual tensor types, graph dimensions, tokenizer semantics and template bytes; family names and filenames are insufficient compatibility evidence.
- Use the publisher FP16 reference file first. Use F32 numerical fixtures and a reproducibly derived F32 development artifact. Required quantized execution follows in G4.
- Preserve all C01–C23 release requirements and C24 image understanding; retain C25–C28 embedding inference/API/CLI/RAG interoperability and add C29–C38 session/tool/constraint/batching and independence/presentation requirements. A CPU-only or text-only preview does not constitute full v1.0.
- Retain mandatory Metal qualification for the pinned 0.5B model in FP16 and Q4_K_M. Add the selected LLaVA and Qwen-VL variants to CPU/Metal qualification under M0–M2/G5. No VLM/backend combination is currently qualified.

## G0 — Foundation and reproducible evidence

1. Initialize Git and the Rust workspace. Pin the current stable Rust toolchain (1.99.1 at the latest dependency refresh) and lock dependencies. Begin with `coheryn-engine`, `coheryn-cli`, and `coheryn-bench`; retain engine modules until stable crate boundaries emerge. Configure formatting, Clippy, tests and CPU builds for macOS ARM64, Linux x86-64 and Windows x86-64.
2. Permit general-purpose serialization, tokenization, templating, threading, HTTP and platform libraries. Coheryn implements graph execution and numeric kernels. External inference/reference tools stay outside production dependencies. Forbid unsafe code in the initial workspace and isolate any future exceptions with documented safety invariants.
3. Pin Qwen/Qwen2.5-0.5B-Instruct-GGUF revision `9217f5db79a29953eb74d5343926648285ec7e67`, file `qwen2.5-0.5b-instruct-fp16.gguf`, SHA-256 `8e0ae26000627ed62de0e78e41860af70094558b9d2913385c842a6aa06cf3fc`. Record exact bytes, licenses, tensor inventory, tokenizer/template identities and reference revisions. Store large artifacts in ignored caches.
4. Build the separately executed, pinned external reference engine oracle. Capture prompt bytes, tokenizer IDs, layer activations, teacher-forced logits and greedy continuations. Include English, Bengali, Unicode, whitespace, explicit/default system prompts, multi-turn chat and special/EOS tokens. Compare identical files and F32 KV settings. Freeze tolerances in `fixtures/models.json`; keep executor parity distinct from quantization quality.
5. Record compiler, hardware/OS, model identity, context, threads, backend, cache dtype and profile. Separate loading, tokenization, prefill, decode and output delivery. Record reservations and observed OS memory separately; mark unavailable counters null. Define hostile-file, mutation, template, allocation, acquisition and cancellation threats.

**Exit:** pinned inputs and scripts reproduce independent correctness evidence and benchmark records. No production dependency executes an external inference engine. Hardware-specific benchmark qualification remains explicit.

Library interfaces are `inspect`, `validate`, `Model::load`, `Model::generate` and the development `trace` observer. Shared types describe model dimensions, diagnostics, resource limits, generation settings, events, usage and finish reasons. Treat these Rust interfaces as unstable until G2. No HTTP server is required for G1.

G1 has a conservative reservation budget, not instrumentation of every tokenizer-library allocation. G3 adds hardware probing, multi-request admission and engine session buffer-capacity observations; complete allocator measurement remains outstanding; do not claim an OS hard memory cap. The initial scalar numerical baseline uses F32 products, activations and outputs with wider scalar reductions to avoid reference roundoff; optimized F32 accumulation requires separate parity qualification. Oracle build flags explicitly disable native ARM half accumulation and SIMD approximations. Frozen numerical tolerances remain unchanged.

## Validation and release rules

- Fast checks: parser/shape fixtures, tokenization/templates, numeric kernels, sampling, admission, cancellation, stop handling and cleanup.
- Model checks: pinned-file logits, layers and greedy outputs separately for every qualified encoding/backend. Never label mere parsing as inference compatibility.
- Embedding checks (planned): exact dimensions, tokenizer/masks/pooling/normalization, individual/batch and CPU/Metal vector parity, explicit truncation, quantized executor/quality separation, CLI/API/SDK/RAG interoperability, peak memory and bounded batch/error/cancellation behavior.
- Image checks: pinned processor pixels/tensors/patches, vision features, projected embeddings/positions and image-conditioned logits/greedy text; single/multiple images, reordered parts, resolutions, formats, component mismatches, Base64/URL security, admission and stage cancellation. Reference tools stay outside production dependencies.
- Security/lifecycle: fuzz hostile metadata; request/auth/path/download limits in G2; repeat requests/cancellations/swaps and active unload tests before release.
- Memory/performance: contexts 128/512/4096 where admitted; concurrency one/two; balanced/low-memory profiles after implementation; cold/warm only when controlled. No speed or memory advantage claim without comparable evidence.
- Default development is CPU-first on macOS ARM64, one inference session, no telemetry. Reject infeasible requests rather than changing context or semantics.
- Maintain the C01–C38 evidence checklist, including session/cache/store/tool/schema/batching, clean-environment independence and controlled-name CI gates. GUI, audio, image generation, video, architectures beyond the mandatory text/VLM targets, Safetensors, CEAP, speculation and SSD paging remain outside mandatory core delivery.

See `RELEASE_CHECKLIST.md` for current evidence and outstanding gates. A checked-in workflow or fuzz target does not prove that its external campaign ran.

## G3 CPU and M0 implementation evidence

`coheryn-engine::planner` contains the pure versioned planner. The API probes CPU/RAM/swap, reuses loaded metadata, reports CPU placement/transfer and shared weights once, and reserves full queued session capacity atomically. Session reservations transfer into compute without a recheck race. Default concurrency is one; an explicit ceiling up to 16 is bounded by logical CPUs. Low-memory uses smaller validated I/O tiles and exclusive execution; G3 profiles preserved scalar arithmetic and F32 KV; G4 adds bounded row parallelism while preserving per-row reduction order. Known engine vector capacities and OS observations are separate from estimates, and complete allocator instrumentation remains open.

`fixtures/vlm/models.json` pins LLaVA 1.5 7B Q4_K_M and Qwen2-VL 2B F16 component/header/processor provenance; `tools/prepare_vlm.py` reproduces bounded inventories without full-weight downloads. Typed component/content contracts and procedural image inputs are present. Image planning descriptors explicitly return unknown stage costs and inadmissibility. Full hashes, independent image/vision outputs, license/component review and multi-image qualification remain M0 acceptance work; M1/M2 are not implemented. Selected LLaVA M2 depends on G4 Q4_K/Q6_K computation. See `PLANNER.md` and the qualification records for exact evidence and limitations.

## V1.6 embedding scope

C25–C28 make native GGUF embedding execution, single/batch vectors, OpenAI-compatible `/v1/embeddings`, headless `embed` CLI and documented external RAG/vector-store interoperability mandatory. Embedding execution must work without loading a generation model. The consolidated v1.6 specification defines task-aware microbatch planning, fixed/qualified dimensions, model-specific masks/pooling/normalization, usage, response limits, file-export semantics and embedding-space identity. Native Nomic F16/Q8_0 CPU embedding execution is implemented through the Rust library; CLI/API routes and RAG interfaces are implemented in E2. E0 pins Nomic v1.5 F16/Q8_0 files, source/tokenizer/pooling assets and independent vectors; the frozen reference fixtures remain independent inputs. The E1 library planner now reserves real encoder/tokenizer/output stages and atomically hands admissions to execution; E2 now shares bounded residency and scheduling with generation. Full RAG, vector databases, ingestion/chunking, retrieval and reranking remain optional packages outside the engine dependency graph.

## G4 CPU implementation and E0 reference preparation

Native packed Q8_0/Q4_0/Q4_K/Q6_K and the Q5_0 type found in the publisher's 0.5B Q4_K_M recipe share bounded buffered storage, checked matrix rows and reusable activation quantization. Request-owned row workers preserve reduction order and reserve their stacks; scratch, one attention score row and prefill chunk boundaries are reused. Prefill remains sequential inside chunks, and packed execution does not retain dequantized model weights. `threads` is propagated through planner, standalone CLI, daemon requests and integrated benchmarks.

[QUANTIZATION.md](QUANTIZATION.md) documents frozen operation fixtures, pinned file inventories, model/service qualification and reproducible measurement commands. Exact-file/platform status lives in `fixtures/compatibility.json`; broader SIMD, cache representations, GPU and platform qualification remain open. Quantized executor correctness compares identical weights; separate quality observations compare quantized references with FP16.

[The E0 guide](../fixtures/embedding/README.md) records byte-verified Nomic v1.5 F16/Q8_0 files and source assets, independent tokenizer/encoder/pooling/vector evidence and mixed-length/duplicate batch comparisons. The 768-dimensional contract and precision criteria are frozen before E1. An offline integrity/consistency check runs in CI. E1 now executes these exact files natively on macOS ARM64 CPU; `/v1/embeddings` and `embed` now expose those vectors through E2. external reference engine execution/comparison benchmarks remain pending.

E1 binds the distinct `nomic-bert` bidirectional encoder and model-specific WordPiece normalization to shared bounded matrix/storage/worker primitives, with mean/L2 pooling, ordered microbatches, immutable admissions and cancellation cleanup. The 50-case multilingual corpus checks token IDs and both native model vectors; its coverage does not establish proficiency in every language. [EMBEDDINGS.md](EMBEDDINGS.md) records limits and evidence. See [EMBEDDING_API.md](EMBEDDING_API.md). M0 still needs independent vision outputs/full asset review before M1/M2 image execution claims; Metal follows the respective CPU graphs.

G4 qualification now covers all four pinned 0.5B quantized files, plus 1.5B FP16/Q4_K_M. The primary files retain all eight greedy cases and 50 layer/logit comparisons each. The second-size files pass all eight tokenizer/render cases, exact primary fingerprints, targeted greedy/profile checks and 58 layer/logit comparisons each under the frozen manifest contract. `g4-service.json`, `g4-planner.json` and `g4-benchmarks.json` provide actual daemon, concurrent-admission and measured profile evidence.
